# v2.3 Design Audit — Context Safety & Recall

## Scope decision

The project remains a repository context reducer, not a persistent personal-memory system or general knowledge engine. Runtime/sandbox/multi-agent components remain optional harness capabilities. Core is `Reduce → Verify → Recall`.

## Design iterations

1. **Initial HOT/WARM store** — rejected because it duplicated every repository locator into a second JSON state file.
2. **Single WARM source** — `.repo-context/index.json` became the only recallable locator store; session Context Store became a HOT overlay.
3. **Module-level recall** — file-structure-only hydration was insufficient for constants/errors outside symbols; bounded ±2-line snippets were added.
4. **Tombstone recovery** — deleted/recreated files could remain blocked by an old missing tombstone; refreshed-index reconciliation now clears recoverable tombstones.
5. **Retrieval precision** — graph-neighbor score originally created standalone candidates and exact lookups carried low-signal tails. Graph is now rerank-only and strong hits prune weak candidates.

## Safety invariants

- Not model-visible does not mean deleted.
- WARM repository locators have one source of truth.
- Recall adds zero required model calls.
- Recalled repository text never gains instruction authority.
- Changed/missing HOT evidence cannot be silently reused.
- `unknown` is valid verification output.
- Similarity has no proof/merge authority.
- No-result recall escalates rather than fabricating evidence.
- Hydration is token-bounded and source-local.

## Current limitations

- Lexical/local-source/graph recall does not guarantee semantic completeness.
- Dynamic-language call graphs remain conservative.
- Non-Git revision identity is weaker than Git blob identity.
- The benchmark fixture is intentionally small; larger real-repository recall suites should be added before claiming broad recall percentages.
