# 架構問題與衝突稽核報告

**專案**：agent-repo-context-reducer v1.3.0
**稽核日期**：2026-08-13
**稽核 commit**：`a48a976`（main）
**稽核環境**：macOS (darwin 25.0.0) / Python 3（Homebrew，`/opt/homebrew/bin/python3`）

## 摘要

專案**功能面是健康的**：69 個測試全數通過，45 個模組之間無循環依賴，零第三方相依。

問題集中在三個軸線：

| 軸線 | 性質 | 嚴重度 |
|---|---|---|
| 文件與實作脫節 | README / CLI help / manifest 描述的行為與程式碼不符 | 中～高 |
| 單一事實來源重複 | 指令定義、能力清單、狀態儲存各有 2～3 份 | 高（已實際漂移） |
| 專案定位擴張 | 約半數模組屬 advisory-only harness，與專案名稱不符 | 中（設計層級） |

其中**只有一項是真實的功能破損**（第 1 節，發佈的指令檔在正式安裝情境下會失效）。其餘為文件漂移與設計債。

## 1. 【P0】發佈的指令檔在正式安裝情境下會失效 (A)

### 現象

`commands/reducer-repo.md:13` 與 `adapters/codex/reducer-debug/SKILL.md:12`（以及其餘 8 個同類檔案）寫死了相對路徑指令：

```bash
python scripts/repo_context.py run reducer-repo "$ARGUMENTS" --repo . --pretty
```

### 兩個獨立的失效原因

**1a. 相對路徑無法跨安裝情境解析**

`README.md:254` 主推的安裝方式是全域安裝：

```bash
npx skills add tommy771004/agent-repo-context-reducer -g
```

全域安裝後，Skill 位於 `~/.claude/skills/`，但使用者是在**自己的專案目錄**下呼叫 `/reducer-repo`。此時 `scripts/repo_context.py` 相對於使用者專案解析 → 檔案不存在 → 指令失敗。

**1b. `python` 指令在現代 macOS 上不存在**

實測結果：

```
$ python -m unittest discover -s tests
(eval):1: command not found: python

$ which python3
/opt/homebrew/bin/python3
```

macOS 自 12.3 起移除 `python` shim。受影響的位置不只指令檔：

| 檔案 | 行號 | 內容 |
|---|---|---|
| `README.md` | 291 | `python scripts/repo_context.py map . --pretty` |
| `README.md` | 762 | `python -m unittest discover -s tests -v` |
| `README.md` | 768, 774 | 範例指令 |
| `README.zh-TW.md` | 同上對應位置 | |
| `package.json` | 7-15 | 全部 8 個 npm script |
| `commands/*.md` | 各 5 檔 | |
| `adapters/codex/*/SKILL.md` | 各 5 檔 | |

### 諷刺之處：正確解法已經存在但沒被使用

`repo_context/host_adapters.py:12-26` 的 `_runtime_command()` 有完整的解析邏輯：

```python
def _runtime_command(project_root: pathlib.Path) -> str:
    exe = shutil.which("repo-context")
    if exe:
        return shlex.quote(exe)
    package_root = pathlib.Path(__file__).resolve().parents[1]
    script = package_root / "scripts" / "repo_context.py"
    if script.exists():
        return f"{shlex.quote(sys.executable)} {shlex.quote(str(script))}"
    ...
```

它會優先找 PATH 上的 `repo-context`，找不到才用 `sys.executable`（正確的 Python 路徑）加**絕對路徑**腳本。

已 commit 的檔案與這個產生器**已經漂移**。實測比對：

```
產生器輸出：  repo-context run reducer-repo "$ARGUMENTS" --repo . --pretty
已 commit：   python scripts/repo_context.py run reducer-repo "$ARGUMENTS" --repo . --pretty
```

（其餘內容逐字相同，僅 runtime 字串不同 → 證實 commit 的檔案是舊版產生器輸出的手工快照。）

### 建議

1. 刪除 `commands/` 與 `adapters/codex/` 的手寫副本，改由 `repo-context host-install` 產生。
2. 若必須保留（作為 GitHub 上的可讀範例），加一個測試斷言檔案內容等於 `render_claude_command()` / `render_codex_skill()` 的輸出，防止再次漂移。
3. 全專案文件的 `python` 一律改為 `python3`。

## 3. 【P0】`host-install` 會把機器專屬絕對路徑烤進專案檔 (B)

`host_adapters.py:18-25`：當 PATH 上沒有 `repo-context` 時，產生的指令檔會包含 `sys.executable` 與**絕對路徑**：

```
/opt/homebrew/bin/python3 /Users/xieyuanyou/Documents/agent-repo-context-reducer/scripts/repo_context.py run ...
```

而 `README.md:199` 教使用者用 `--scope project`：

```bash
repo-context host-install --host claude-code --scope project --repo .
```

`--scope project` 會寫入 `.claude/commands/`（`host_adapters.py:43`），這是**會被 commit 的路徑**。一旦提交，對團隊其他成員（不同 home 目錄、不同 Python 路徑）全部失效。

### 建議

專案範圍的安裝應產生可攜式指令（優先 `repo-context`，或相對於 repo root 的路徑）；絕對路徑僅用於 `--scope global`。或至少在 `--scope project` 時輸出警告。

`README.md:637-653`「Incremental Cache」章節只提到 `.repo-context-cache/`。完全沒說明所有看似唯讀的指令都會寫出 `.repo-context/index.json`。

### 問題 4b：兩者都未被 gitignore

```
$ git check-ignore -v .repo-context .repo-context-cache
(exit 1)
```

本 repo 根目錄**沒有 `.gitignore`**。任何使用者裝了這個工具、在自己的 repo 跑一次，`git status` 就會多出兩個未追蹤目錄。

專案自己的測試知道要處理這件事 —— `tests/test_repo_context.py:114`：

```python
(root / ".gitignore").write_text(".repo-context-cache/\n", encoding="utf-8")
```

但產品本身不會替使用者建立。

### 問題 4c：雙份狀態、內容重疊 (C)

| 目錄 | 內容 | 失效機制 |
|---|---|---|
| `.repo-context-cache/summaries-v2.json` | 每檔結構摘要 | path + mtime + size（`cache.py:13`） |
| `.repo-context/index.json` | 完整索引，**內嵌同一批摘要** | 整檔覆寫（`indexer.py:33`） |

同一份資料存兩次，兩套失效邏輯。對本專案（4,405 行）就要 320KB。

### 建議

1. 首次寫入狀態時自動建立／追加 `.gitignore`（`.repo-context/`、`.repo-context-cache/`）。
2. README 補上寫入副作用說明與 `--no-sync` 旗標。
3. 中期：合併為單一狀態目錄。

## 5. 【P1】`sync` 宣稱增量，實作是全量重建 (B)

`cli.py:64` 的 help 文字：

> `Incrementally refresh the native persistent index`

實際實作（`indexer.py:37-59`）：

```python
def ensure_index(root, sync=True, **kwargs):
    existing = load_index(root)
    ...
    previous_paths = {f["path"] for f in existing.get("files", [])}
    result = build_persistent(root, **kwargs)     # ← 完整重掃 + 重建圖 + 重排序 + 整檔覆寫
    current = result["index"]
    current_paths = {f["path"] for f in current.get("files", [])}
    stats.update({
        "added_files":   sorted(current_paths - previous_paths)[:100],
        "removed_files": sorted(previous_paths - current_paths)[:100],
    })
```

真正增量的只有 `SummaryCache` 這一層（省下重新 parse 檔案內容）。以下全部重做：檔案列舉、依賴圖建構、ranking、JSON 序列化與寫檔。`added_files` / `removed_files` 是**事後 diff**，不是增量計算的依據。

目前小專案上是 0.2s，感覺不到。但這是 `map` / `query` 等所有指令的**預設路徑**，在大型 repo 上會成為主要成本 —— 而這正是本專案宣稱要服務的場景（`README.md:688`：「The design targets medium and large codebases」）。

唯一的規避手段是 `--no-sync`（`cli.py:53`），README 通篇未提。

### 附帶：`rank_files` 每次指令重複計算 (B)

| 位置 | 呼叫 |
|---|---|
| `scanner.py:204` | `build_index()` 內部已排序一次 |
| `scanner.py:229` | `project_map()` 再排一次 |
| `scanner.py:266` | `module_map()` 再排一次 |
| `scanner.py:290` | `changed_view()` 再排一次 |

`build_index` 回傳的 `files` 已是 `ranked`，但下游一律重排。（`project_map` 需要傳入 `query` 才有意義，但無 query 時是純粹浪費。）

## 8. 【P3】架構層級評論 (C)

### 8a. `cli.py` 是 god module

- 578 行
- 45 個 subparser（`build_parser()` 佔 `cli.py:57-220`）
- 單一 `if/elif` 巨型分派（`cli.py:343-569`）
- 混入商業邏輯：`_auto_delegate_trusted()`（`cli.py:291-323`，33 行）、`_symbol_with_ledger()`（`cli.py:247-261`）

45 個模組之間的依賴圖其實很乾淨（無循環，`storage.py` / `util.py` 是共用底層），代價是**所有接線都塞進 CLI**。這是全專案唯一的整合點，也是最脆弱的地方。

**建議**：command 註冊與 handler 改為表格驅動；把 `context` 分支（`cli.py:475-537`，63 行）抽成獨立模組。

### 8b. 專案定位與名稱不符

專案名為 `agent-repo-context-reducer`，但 45 個模組中約有一半屬於多代理 harness：

```
complexity, risk, model_router, lane_budget, scheduler, grader, retry_policy,
orchestration, fanout, voi, attribution, benchmark, admission
```

而這些**全部是 advisory-only、不執行任何東西**。程式自己寫著（`cli.py:513`）：

```python
result["orchestration"]["execution"] = "advisory-only; this command does not spawn agents"
```

`README.md:456` 也坦承這點。

造成兩個後果：

1. 使用者為了「reduce repo context」而安裝，卻要理解 15 層 harness 概念（`references/architecture.md:46-62`）。
2. 這些純啟發式模組沒有真實執行回饋，其建議品質無從驗證。

這是可以誠實面對的取捨 —— 但至少該在 README 開頭把「repo context reducer」與「harness planner」切成兩個明確的產品面向，而不是混在同一個 Repository Layout 裡。

### 8c. 值得注意的設計取捨（**不是 bug**）

`cli.py:496-498`：

```python
elif not native_needed and blocks:
    index = _empty_index(root)      # 完全跳過原生 index
    native_index_used = False
```

當有可信任的外部 provider 成功 delegate、且路由判定不需要原生 repository 能力時，**原生程式碼圖會被整個略過**。

這**符合** `SKILL.md:44` 宣告的政策（「Reuse before implementing」），但意味著輸出品質會隨環境靜默變動。所幸 `provider_delegation.native_index_used`（`cli.py:518`）有回報，具備 provenance。

列在此處是為了讓維護者意識到這條路徑的存在，而非要求修改。

### 8d. 打包範圍不完整

`pyproject.toml`：

```toml
[tool.setuptools.packages.find]
include = ["repo_context*"]
```

`pip install` 只打包 Python 套件。以下不在 wheel 中：

- `references/**` —— `SKILL.md:64-75` 的「Progressive reference routing」明確指引模型去讀這些檔案
- `scripts/repo_context.py` —— `host_adapters.py:19` 的回退路徑
- `examples/**`、`commands/**`、`adapters/**`

目前 `_runtime_command()` 會先找到 PATH 上的 `repo-context` 所以不致失效，但 **references 路由在 pip 安裝情境下是斷的**。

## 9. 該給的公道：本專案做得好的地方

以下**不算衝突**，不應與上述發現混為一談。列出是為了讓真正的問題更有說服力。

- **誠實的能力邊界宣告**。`references/architecture.md:96-98` 明確承認：

  > The Python harness can control what **it** emits. A Skill alone cannot universally intercept every built-in Read/Grep/tool call of every agent. Hard enforcement requires host-runtime hooks/plugins/MCP/tool-gateway integration.

  這在同類專案中相當罕見。

- **「不是 GraphRAG」「不是 runtime call graph」的免責一致且落實到程式輸出**。文件三處重複（`SKILL.md:89`、`architecture.md:80-84`、`README.md:127`），程式輸出也帶對應欄位：
  - `cli.py:548` → `"graph_semantics": "resolved static import graph; not a runtime call graph"`
  - `cli.py:554` → `"not_provided": "runtime callers"`
  - `cli.py:562` → `"runtime_impact_guarantee": False`

- **token 估算明確標示為近似值**，非計費依據（`README.md:686`、`SKILL.md:106-108`、`scanner.py:259`）。

- **依賴結構乾淨**。45 個模組無循環依賴，`storage.py` / `util.py` 作為共用底層，耦合控制良好。

- **安全預設合理**。secret-like 路徑、私鑰、symlink、binary、generated code 一律排除（`util.py`、`scanner.py:114-127`），`inspect` 亦拒絕 secret 路徑（`cli.py:235-236`）。

- **零第三方相依、69 個測試通過**，符合 `README.md:778` 的宣稱。
