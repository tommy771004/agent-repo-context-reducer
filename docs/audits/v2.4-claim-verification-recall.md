# v2.4 Design Audit — Claim-Aware Verification Recall

## Why this exists

A read-only benchmark against a real React/TypeScript UI repository exposed three common partial-context traps:

- `bottom-0` looked like a universal bottom sheet until breakpoint overrides were recalled;
- importing a motion helper looked like using it until invocation search found no call;
- a large i18n catalog looked complete until rendered hard-coded copy was inspected.

The fix is not to send more files by default. The fix is a bounded verification-recall path that searches for evidence capable of changing a provisional conclusion.

## Rejected designs

- **Run a second LLM grader for every claim** — unnecessary token/cost amplification.
- **Treat regex hits as semantic truth** — unsafe; patterns can match comments, tests, or non-visible code.
- **Always search the whole repository** — increases noise and makes negative evidence meaningless.
- **Automatically downgrade/upgrade runtime mode on every observation** — couples a core context primitive to the optional runtime harness.

## Implemented boundary

The core returns evidence and observations only. Runtime orchestration remains optional. Hosts decide whether a challenged/inconclusive claim deserves another reasoning turn.

## Known limitations

- Rule-derived verification dimensions are intentionally finite; unknown claim types fall back to lexical context recall.
- Search absence is meaningful only when scope is bounded and complete.
- Syntax-aware invocation/reference verification is still preferable when a language parser can prove it; v2.4 search observations remain provisional.
- Provider-billed token/latency savings require provider telemetry; native bytes/4 estimates are not billing claims.
